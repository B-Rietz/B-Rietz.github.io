Lennar · Agentic workflow · Claude Code

My own small software factory

I set up a Claude Code workflow that took my tickets from investigation all the way to a pull request, with human checkpoints so nothing reached production without someone saying yes. I used it every day, and teammates adopted it. It also became my best research into where agent tools confuse people.

RoleDesigned, built, and used daily
StackClaude Code · Salesforce · GitHub · Obsidian
AdoptionA couple of teammates adopted it
ResultAbout 2x faster delivery
Before

Every ticket started from zero.

Tickets were queuing up faster than they shipped. Bugs surfaced late, in code review or QA, where they cost the most to fix. And the architecture and business rules lived in people's heads, so each ticket began with re-investigating how things worked.

Each stage of the pipeline answers one of those: a knowledge base so runs start with context, tests and a browser check so mistakes show up before review, and a human approval so speed never costs safety.

How it worked

Guardrails. Production CLI deployments were blocked outright. Other sensitive actions required explicit authorization.
Memory. A Git-backed Obsidian knowledge base of our architecture and business rules, which the agent kept up to date, so every run started with context.
What living inside it taught me

Agents are magical until you have to trust one.

What is it doing right now?

Long runs turned into a black box. I wanted progress I could read at a glance, not a scrolling log.

When should I step in?

Some moments needed me, and most didn't. The tool couldn't tell the difference, so I had to watch everything or risk missing the one that mattered.

Can I trust what it made?

The tests, browser checks, and QA notes existed so I could trust the result without re-reading every line. Evidence beat explanation.

In practice, the tests and the browser check caught problems before they ever reached a pull request. Building evidence into the loop meant the agent's mistakes showed up while they were still cheap to fix, not after someone had already approved them.
Why it matters for design

These are interface problems.

None of those three questions is solved by a smarter model alone. They're about visibility, attention, and evidence: what the tool shows you, when it interrupts you, and how it proves its work. That's the design space I want to work in, and it's where my concept work picks up.
